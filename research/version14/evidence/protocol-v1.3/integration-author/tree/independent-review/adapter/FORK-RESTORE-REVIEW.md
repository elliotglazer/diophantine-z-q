The fork reader keeps the protected base repository as the sole API origin. The authenticated PR response supplies the head repository's positive integer ID and syntactically checked name. Exact `refs/pull/N/head` and `refs/pull/N/merge` responses from the base repository must match the PR head and merge commits. The current base ref and ordered merge parents still bind the current base/head pair. Object, source and CI reads stay under the base repository URL; candidate-provided fork URLs never become request destinations.

The run must belong to the protected base repository, while its head-repository ID and the selected PR association's head-repository ID must match the authenticated fork ID. Current PR number, base SHA and head SHA remain required. Missing associations, wrong fork IDs, wrong pull-ref names, changed pull-ref commits and noninteger fork identities fail the independent tests. Required workflow/source pins, latest selected run, exact current attempt, jobs and successful actual steps remain the accepted parent's rules. Empty CI association or absent jobs still fail; no fallback was added for the previously observed incompatible sample.

The reader's full observation retains fork identity and both pull refs. The live profile compares that state with the registered capture and repeats the observation after actual core/evidence checks and during every recheck. Independent tests confirm a new pull-ref value invalidates an existing session, while the current collector and policy safeguards still reject revocation or changed source configuration. These reads have the same explicit non-atomic cutoff as the parent evaluator. The result is not a portable authorization and does not itself publish a check.

Restoration first deep-copies the submitted records and expected checkpoint and verifies the full signed chain using the correct operator or intake codec. It requires an absent protected destination and compares the supplied checkpoint to the existing authoritative anchor. It writes a new same-directory temporary SQLite file, commits and closes it, checks the anchor again, and atomically links it to the destination without replacing an existing file. It then returns only after the accepted store performs its verified read against that anchor. The helper never calls anchor initialization or compare-and-swap during restoration.

The independent filesystem tests confirm that a file created at the destination immediately before installation is preserved; a failed hard link cleans up the temporary file; stale or tampered input creates no destination; and an anchor change after installation rejects the operation while retaining the stale local mirror for inspection. A wrong ledger domain is rejected. A valid empty intake genesis can be restored only against that already existing authoritative genesis. Lack of hard-link support fails rather than silently switching to an overwriting rename.

The returned accepted store still calls the supplied anchor on later reads and appends. This helper does not make an in-memory or candidate-supplied checkpoint durable. Its deployment caller must supply the independently reviewed remote authority, transport the new signed entries and checkpoint together, and handle interrupted publication. A simple anchor that updates a remote checkpoint while leaving the new entries only in the ephemeral local database would violate that contract. A working controller integration must test this explicitly; this report does not infer it from successful restoration tests.
