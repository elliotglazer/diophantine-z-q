# Git state persistence review

Accepted for bounded remote load/append persistence at `git_state.py` SHA-256 `76269c5918bdf81d40e58685a9c207faa85f342cf0cd79e4d8a9203e7ea87815`, after correction of the findings below. The source is `work/protocol-ruleset-20261107/controller/git_state.py`. This review does not cover a future initializer, authenticated HTTP client, ledger transition validator or publisher. No remote state was created or changed.

The initial source, SHA-256 `fe7237d42e7aea0a878cfac8760031fd59bd2fae9be74bfd6d8da7e4316b9d3b`, is preserved as `git_state_original.py`. `original-probes.log` preserves all three failing independent tests.

The initial `Snapshot` dataclass was shallowly frozen. Its dictionaries remained mutable, and `append` trusted the caller's `entries`, index and tree. Removing an existing path from `snapshot.entries` allowed `append` to overwrite its original bytes; a subsequent `load` accepted the rewritten entry. Constructing a snapshot with the real current commit but an unrelated tree and empty inventory similarly removed all historical entries while producing a loadable successor. Caller-side signed-ledger checks could detect some consequences, but the persistence layer's immutable-history contract did not hold. The corrected `append` uses the supplied snapshot only as an expected-commit token and reloads authoritative remote state before deriving its tree, metadata or entry contents. Both independent reproductions now preserve the original history.

The initial identity check also accepted JSON numeric `42.0` for configured repository ID `42`. The corrected code requires an exact integer, consistent with the previously accepted components' binding discipline. The third negative test now rejects that value.

All 27 tests passed against the corrected source: 12 author tests and 15 reviewer-built tests. The reviewer tests use their own bounded Git REST simulator and do not import author test helpers. They cover round-trip bytes, unchanged and conflicting old entries, altered/constructed snapshots, stale expected tips, a competing writer just before ref update, a lost response after successful update, unapproved paths, duplicate JSON keys, blob tampering, missing indexed history, executable modes, truncated trees, and capacity limits. `corrected-probes.log` and `author-tests.log` contain the results. Run `python -B probe_state.py <absolute-path-to-git_state.py>` from this directory; without an argument it deliberately targets the preserved defective source and demonstrates the original failures.

I inspected the complete source and the two corrections. Load checks the private repository identity, exact state ref, commit/tree response identities, nontruncated inventory, supported file paths and modes, complete index membership, immediate parent correspondence, bounded file counts/entry sizes/aggregate entry bytes, Git blob hashes, raw SHA-256 digests, and a stable final remote tip. Append reloads that state, refuses differing bytes at old paths, retains its tree as the base, appends metadata, and creates a new commit with exactly the old tip as parent. It updates with `force: false` and confirms the resulting tip. Concurrent siblings are rejected by the GitHub fast-forward contract, which the simulator models. This review did not independently exercise the live GitHub endpoint.

The remote ref remains the current authority. This module does not authenticate its HTTP transport, enforce branch protection, or detect an administrator restoring a matching old commit. Its caller must provide the protected fixed-origin transport, configured numeric repository identity and suitable credential scope. The implementation checks the API's authenticated commit/tree descriptions rather than reconstructing their object hashes locally; it does independently hash every returned blob. These are explicit trust assumptions, not cryptographic protection against a dishonest GitHub server.

Checkpoint dictionaries are deliberately opaque here. The caller must verify the signed operator/intake chains, expected ledger identities and monotone checkpoint transitions before calling `append`. Path sequence formatting alone does not establish ledger sequence validity. The store preserves old bytes but does not make an arbitrary new checkpoint semantically valid. A restored cached snapshot cannot overwrite newer remote history because its expected commit is stale; restoration of the trusted remote authority itself remains outside scope.

The 512 MiB bound applies to indexed entry payloads, with a separate bounded index blob. It is not a strict overall process-memory ceiling or total-repository-history limit. JSON responses must also be bounded by the eventual HTTP transport. A failed write may leave unreachable Git blobs/trees/commits, but no success is returned until ref publication is confirmed. A lost response after a successful ref update raises and leaves the new state readable; the caller must re-read and reconcile this ambiguous outcome instead of blindly retrying stale state. Genesis creation and crash recovery across a separate App check write still need their own reviewed implementation.
