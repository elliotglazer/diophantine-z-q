# Read-only GitHub context collection

`github_read_context.py` is a read-only observation component. It does not publish a check, authorize a merge, authenticate model sessions, or complete the ledger bridge. Its tests use synthetic transport responses and no real credentials. The component preserves the accepted ledger, store, bridge, manifest collector and schema-2 core unchanged.

## Explicit protected configuration

The trusted process constructs `TrustedPolicy` from operator-controlled configuration outside candidate write access. Configuration supplies the numeric repository ID and exact owner/name, permitted base branch, old policy path and SHA-256, protected path prefixes, and required workflow policies. Each workflow policy gives its numeric ID, path, exact job-name set, exact reusable-workflow response records, and SHA-256 pins for its complete approved local execution inputs.

The source map must include the workflow file and its relevant scripts, composite actions and configuration. The operator must establish this closure and review what the approved workflow actually executes. This component does not parse arbitrary YAML or prove that a workflow performs useful tests. Candidate tests can contain malicious or vacuous behavior; a successful Actions job is not a proof of mathematics or correct test coverage. Installing a source map copied from the candidate would violate the trust contract. No loader turns repository JSON or `trusted: true` into protected policy.

The policy and every registered workflow input must retain the approved bytes in the current base, candidate head and current two-parent merge tree. A policy/workflow update therefore fails the ordinary observation path. Separately reviewed promotion of protected configuration is required; this module does not implement policy promotion. It also conservatively rejects forks, drafts, non-PR workflow events, missing merge commits, and merge commits that do not have exactly the current base/head as their ordered parents. Those limitations may block legitimate work, but do not silently weaken provenance.

## Network and complete collection

`GitHubHTTPS` uses standard-library TLS to the fixed host `api.github.com`, port 443, with GET requests only. It does not use environment proxy configuration, redirects, candidate URLs, shell commands, checkout, or candidate execution. Optional credentials arrive directly from the trusted caller. No request headers, response bodies or credentials are logged. Transport errors have generic messages. Responses must be HTTP 200 JSON, at most 16 MiB, and uncompressed. Duplicate JSON keys and nonfinite numbers are rejected. The injected transport exists for testing and is part of the caller's trusted boundary, not an authenticated data format.

The pagination reader accepts only same-origin, same-endpoint links with identical filter parameters and sequential page numbers. It rejects duplicate record IDs, changing counts, incomplete totals and unsupported links. Each collection has a 100-page limit; a reader has a 5,000-request limit. These are fail-closed resource limits. Filtered workflow-run results at or above 1,000 are rejected because GitHub documents a 1,000-result search cap. No partial result is reported as complete. Array endpoints do not expose totals; their documented pagination links and a second complete pass provide the available observation boundary. See GitHub's [pagination documentation](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api) and [workflow-run API](https://docs.github.com/en/rest/actions/workflow-runs).

Collection reads the numeric repository identity, open PR, current base branch ref, and exact base/head/merge commit trees. The base/head manifests are first checked by the accepted full-manifest verifier; their commit/tree values must match the API observations. Registered source files are resolved through untruncated nonrecursive API trees and their actual blob bytes are checked against Git object IDs and SHA-256 pins. The complete manifest binding uses the same schema-2 canonical hashes as the existing bridge. No sparse proxy manifest is substituted.

The current PR conversation, submitted reviews and line comments are each fully paginated. Original API records and bodies are returned in the observation. A second complete pass must match the first byte-for-byte under canonical JSON. A final PR/base/commit pass must also match. This detects changes visible across these reads; it is not an atomic GitHub snapshot, cannot rule out change-and-revert between reads, and provides no guarantee after the last request or while the local tool is stopped.

## CI provenance and success

For every configured workflow, collection checks the API workflow ID/path and active state, then reads all workflow runs filtered by the exact candidate head. It chooses the highest run ID, so a newer failing or wrong-event run cannot be hidden behind an older green run. The selected run must be a `pull_request` run in the configured repository, with the exact workflow ID/path, candidate head, and an API PR association containing this PR number and exact base/head commits and repository IDs. Missing association is a failure. The actual run must be `completed` with conclusion `success`.

Jobs come from the selected run's exact current attempt endpoint. Every configured job must appear exactly once, and no unregistered job can be silently ignored. Each job must match the run ID, attempt and candidate head and have status `completed`, conclusion `success`. Its step list must be nonempty, and every returned step must also be completed/successful. Neutral, skipped, pending, failed or missing work fails. This intentionally strict rule can require refinement for an independently reviewed workflow with optional steps; no such exception exists now. Workflow/run inventory, attempt and jobs are collected twice and compared before returning. The [workflow-job API](https://docs.github.com/en/rest/actions/workflow-jobs) documents the attempt-specific job endpoint.

GitHub's Actions API identity is an observation from the trusted service, not a distinct check-publisher identity and not cryptographic proof of runner behavior. Source pins and exact run associations prevent ordinary wrong-workflow/wrong-revision substitutions under the approved CI policy. They do not turn generic Actions into the future isolated App publisher or prove the actual tested checkout when an approved workflow itself is incorrectly designed. The operator must review that semantic requirement when approving the workflow and its dependency closure.

## Durable intake remains required

The result explicitly says `merge_authorized: false`, `deployment_eligible: false`, and `durable_intake_registered: false`. It is an unsigned in-memory observation. Saving its JSON does not authenticate it. `verify_context` always raises `IntegrationMissing`; the existing ledger evidence bridge cannot become live merely by plugging in this object.

The remaining integration must register the captured observation in protected durable state, bind it to the current external ledger checkpoint, and reconcile every registered finding and every ledger report. It must retain previously observed deleted/edited objections and explain their dispositions. Current comments cannot recover deleted comments that were never observed, and GitHub cannot discover unregistered audits conducted elsewhere. A deployment needs an explicit registration/cutoff rule for external audit intake; it must never assert that this collector discovered all historical or external audits. Authentic capture of actual agent observations, protected policy promotion, receipt selection, this reconciliation, final freshness checking at publication, the App publisher, and deployment isolation remain incomplete.

## Reproduction

Run `python -B test_github_read_context.py` in this directory. `run_github_context_checks.py` also reruns the accepted store/bridge tests and records exact file hashes. Fixtures cover changed repository/base/head/PR state, unapproved source files, stale/wrong CI and attempts, missing/skipped steps and jobs, newer failed runs, changing comments, incomplete or hostile pagination, type-confused IDs, JSON ambiguity and redirect rejection. No test establishes a live repository's current CI or authenticates a real session.

## Versioned PR-state projection

The state record carries `projection_schema: github-pr-state/v3`. Both readers use it during capture, evaluation and every freshness check. At the PR response root, only `mergeable`, `mergeable_state` and `rebaseable` are excluded. Raw merge readiness is still checked separately by the publisher.

At the exact repository-object slots, the projection excludes repository-wide activity fields: `size`, `open_issues`, `open_issues_count`, `stargazers_count`, `watchers`, `watchers_count`, `forks`, `forks_count`, `network_count`, `subscribers_count`, `updated_at` and `pushed_at`. A star, fork, new issue or unrelated branch push can change these without changing the reviewed content. These counters and activity timestamps are not proof or CI identities. The saved capture and a subsequent owner-credential PR10 read differed only in star/watch counters and nested repository `updated_at`. The failed App read was not preserved, so this comparison does not establish its exact response bytes.

The repository slots are `pr.base.repo` and `pr.head.repo`, and each CI run's `repository`, `head_repository`, `pull_requests[*].base.repo` and `pull_requests[*].head.repo`. This applies to the selected run and collected run inventory. No arbitrary recursive stripping occurs. The `fork` boolean, identity, visibility, privacy, permissions, configuration and unknown fields remain. The PR's own timestamps also remain.

Title, body, draft/open/merged state, labels, requested reviews, users, commits, trees, branch and pull refs, source pins, complete intake and current required CI retain their checks. All run IDs, attempts, events, associations, workflow identities, jobs and required success conditions remain checked. The publisher still requires raw `mergeable is True` at its readiness boundaries.

Signed older captures remain historical evidence. Do not edit or rehash them as v3 captures. This schema change requires fresh authenticated captures under the reviewed reader and dependency pins. Keep all original records, decisions and findings. New observations do not themselves accept changed semantic evidence.
