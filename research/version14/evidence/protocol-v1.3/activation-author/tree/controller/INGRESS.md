# Protected observation ingress

`ingress.py` is the owner-only controller's signing and state-ingress path. It reads actual observations committed by the trusted owner, verifies full candidate Git contents, captures current GitHub intake, applies only explicitly supplied classifications, and commits signed entry tails and their checkpoints together. It does not create a favorable audit, invent a run identity, publish a check, or modify a ruleset.

The workflow template uses the same `protocol-controller-state` concurrency group as evaluation, with cancellation disabled. It runs only the approved private controller main SHA. The controller checkout, dependency lock and ingress batch come from that approved revision. No candidate checkout, dependency installation, import or program execution occurs.

## Protected inputs

The existing job configuration supplies the exact candidate packet, selected report-ID map, target repository identity, old-policy/workflow configuration, App installation, and the pinned full collector implementation. The ingress batch is an owner-committed JSON file under `controller/ingress-batches/`. A dispatch input only selects that file. It cannot supply inline observations or access files outside the approved checkout.

The batch has exactly these fields:

| Field | Meaning |
| --- | --- |
| `schema` | `protocol-owner-ingress/v1` |
| `id` | Unique immutable owner batch identity |
| `job_id` | Exact configured job ID |
| `mode` | `capture` or `finalize` |
| `key_ids` | Exact `operator`, `intake`, `collector` signer key IDs |
| `operator_events` | Actual plain events in the accepted operator-ledger schema |
| `external_materials` | Explicit external source registrations with original body and observation bytes |
| `findings` | New finding registrations with original body, exact material selectors and observation bytes |
| `classifications` | Explicit source selectors, finding IDs, reason and original observation bytes |

The accepted operator codec requires original tool-observation bytes, observed agent/run identities, frozen target/dependency/binding hashes and original report bodies. Those facts must come from the owner's actual orchestration session. Ingress signs exactly those supplied events with the controller secret registry. A user-written reviewer label, a candidate `verified` flag or a newly invented favorable report is not a substitute. No production observation records are generated by this implementation.

An external material has `source_id`, `body_base64`, and `observation_base64`. A finding has `finding_id`, `body_base64`, `sources`, and `observation_base64`. A classification has `source`, `finding_ids`, `reason`, and `observation_base64`. A source selector is either an exact `material_id`, or an exact pair `report_id` and `report_sha256`. There are no wildcards or implicit latest-version selections. Empty `finding_ids` means an explicit owner-recorded no-finding classification of that exact source, with reason and original observation evidence.

Operator and intake secrets use the runtime's protected key registry format, including `operator_id` and secret bytes decoded only inside Actions. The intended operator identity is `elliotglazer-research-operator`; configured signer IDs are `operator-20261107`, `intake-20261107`, and `collector-20261107`. This code creates no real keys or persistent local key files. It receives existing controller secret values only during the protected workflow.

## Full object verification before collection signing

`BareGitCollector` obtains a scoped installation token through the reviewed App transport's narrow internal `_access()` method. It creates a new bare object store, disables credential helpers, hooks, file protocol, redirects and submodule recursion, and fetches only the configured base branch and `refs/pull/N/head` from the fixed base repository URL. The token is placed in subprocess environment configuration for an HTTPS Authorization header. It is never placed in command arguments, a Git configuration file, a URL, output or an exception. Other protocol secrets and GitHub tokens are removed from the child environment. The controller's system Git executable is trusted.

The fetched refs must exactly match the owner-frozen packet's base/head commits. The unchanged accepted full collector runs in a separate isolated Python process with controller/App/HMAC credentials removed from its environment. Its nested Git subprocesses therefore inherit the sanitized environment too. It traverses and hashes every tree and blob locally, in bounded chunks, with lazy fetch disabled. It retains its limits of 1 GiB per blob and 4 GiB unique blob content per manifest. This supports the repository's files that exceed the JSON API transport's 16 MiB response limit. The collected manifests must match every byte of the packet's canonical full manifests, including unused raw-digest metadata, before any collector envelope is signed.

All Git object acquisition and collector execution are data operations. Repository files are never checked out or executed. The later authenticated GitHub intake read independently verifies live base/head/merge provenance and rejects state movement. A failed collection or mismatch produces no authoritative state append.

## Atomic ingress and history

Ingress first loads and verifies both complete signed logs from the current authoritative `RemoteState`. It stages all operator events, collector envelopes, current intake capture, external registrations, new findings and classifications in memory. The publisher checkpoint is preserved.

`finalize` requires complete durable reconciliation and exact selected current independent receipts for every application, finding and assembly target. `capture` permits unclassified material to remain and returns those exact material IDs. It never treats that pending state as a favorable evaluation. Neither mode runs the publisher.

After validation, one `RemoteState.advance` call supplies all new immutable signed entry files, both replacement checkpoints and an immutable ingress receipt. `GitState` commits them in the same new state generation using its authenticated fast-forward CAS. A concurrent state advance fails rather than losing observations. Existing entry files, historical comments, old negative reports and unrelated publisher state are never removed.

The ingress receipt records the batch digest, packet digest, exact selections, checkpoints, material IDs and pending material IDs. Repeating the exact already-committed batch returns its existing receipt without resigning or recollecting. Reusing its ID with changed input fails. An old receipt is not a claim that current GitHub state is fresh; the live evaluator still performs its own reconciliation and repeated current observations.

## Positive documentation-PR bootstrap

The owner freezes the real documentation-PR packet and obtains actual independent agent reports. The owner commits those original observations and report selections into the private controller, together with exact source classifications. After approving that controller revision, dispatch this workflow with the committed batch path. If every current material revision was already identified, `finalize` can sign and commit the complete batch in one run.

If current comment revisions are not yet known, use `capture` first. Read the private state receipt and original archived materials, perform the actual classification, then commit a new `finalize` batch with exact material IDs and original classification observations. The second batch supplies only new operator/finding registrations; it must not replace existing IDs. The evaluator can then restore the signed logs and evaluate the same exact packet. No mandatory second GitHub-user approval is introduced, and no successful mathematical or protocol review is manufactured by ingress.

Future PRs use the same process. New head/base contents, changed dependencies, new comments or newly observed objections require updated actual reviews or classifications as appropriate. Deleted comments and superseded reports remain in the durable history. Unobserved deletions and unregistered external audits remain outside discovery, under the already documented registration policy.

## Validation and scope

`test_ingress.py` uses synthetic observations, fixture keys, a fake authenticated Git service and actual codecs. It includes a positive ingress-to-live-evaluator path, atomic checkpoint/content updates, exact replay, incomplete classifications, missing/wrong selections, unconsumed blob tampering, concurrent state movement, retained history and fork capture. The bare-fetch test inspects commands/environment without networking and confirms no checkout or token in arguments.

No live API call, real secret creation, owner observation fabrication or state mutation was performed while implementing this component. The root-owned workflow setup, real observation packet, App secret provisioning and final deployment remain separate actions. Runtime and transport dependencies must retain their own exact independent review pins when this ingress is integrated.
