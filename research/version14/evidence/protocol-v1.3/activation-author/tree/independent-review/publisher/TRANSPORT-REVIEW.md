These observations still have the polling cutoff described in the publisher review; pagination cannot make changing GitHub state atomic.

The requested token omits `issues:read`. I inspected the actual live reader and found only `/issues/{PR}/comments`, not separate linked-issue fetching. GitHub accepts pull-request read permission for this comment API, so the omission is not a defect in this composition. A future separate linked-issue collector requires its own permission review. [GitHub issue-comment API](https://docs.github.com/en/rest/issues/comments).

Two live compatibility checks remain part of deployment verification: validate the actual installation token response and verify how GitHub handles a completed check updated to `in_progress` without a conclusion field. The publisher rejects an unexpected response and attempts failure revocation, so the latter uncertainty does not authorize a false success. The mocks alone do not establish that transition's liveness. [GitHub check-run API](https://docs.github.com/en/rest/checks/runs).

No implementation correction was required for this frozen transport. This decision leaves runtime environment decoding, the remote generation authority, actual protected packets, and final rule activation to their separate reviews.
