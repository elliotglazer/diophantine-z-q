# Independent durable-intake review

Accepted within the stated component scope. I found no defect requiring a producer change in the frozen intake implementation. This accepts authenticated intake storage and consistency checks under its explicit trusted-recorder assumptions. It does not accept a live protocol gate, a VerifiedContext implementation, a publisher, or merge authorization.

The review examined the actual three implementation files and documentation, the accepted dependencies they call, the author tests, and separate adversarial fixtures. The reviewer did not author this component, modify its sources, use production credentials, or call GitHub. All tests used synthetic keys and temporary stores.

The completed replay passed 187 tests: 43 new author intake tests, 53 accepted reader tests, 24 accepted store/bridge tests, 44 accepted schema-2 tests, and 23 independently written intake tests. The independent tests use the reviewer's earlier Git trees, HTTP routes, operator events, and store fixtures rather than the author's test helpers. Their complete manifest envelopes are signed with independently assembled HMAC messages. The first run contained one incorrect expected exception message in the reviewer's domain test: operator verification rejected the foreign genesis before checking its MAC. The preserved initial log shows that test failure. The corrected test checks both rejection paths, including an adapted genesis and a valid operator event signed with the wrong domain. This was a fixture correction, not a producer defect.

The authenticated record binds the intake-specific domain, ledger identity, position, preceding hash, key and operator identity, and complete event. The external current checkpoint is required. Edits fail authentication, and intake signatures cannot authenticate operator-ledger messages. The accepted persistence methods `__init__`, `initialize`, `read_verified`, `assert_current`, and `recover_forward` have identical ASTs. The changed `_load` checks aggregate payload bytes and entry counts before decoding the entries; the changed `append` reports a committed checkpoint when external anchor advancement raises. I examined those changes directly. Tests cover count and byte limits, a restored old database with a newer anchor, interrupted anchor advancement, blocked reads, and explicit forward recovery. There is no silent truncation or automatic rollback. These limits are admission limits, not a strict process-memory ceiling for an arbitrarily corrupt SQLite file.

Capture verifies both complete manifests against the protected repository identity, collector code hash, and collector key registry before invoking the configured reader. It retains the signed envelopes and exact packet hash. Reconciliation verifies those envelopes again with the current collector configuration. Changing an otherwise unused raw blob digest, substituting the collector identity, removing its signer, or changing the exact packet prevents success. Full collector provenance still means that the protected signer actually runs the accepted full collector. HMAC possession alone cannot prove blob reading. Candidate-controlled code, signer keys, policy, or reader injection would violate the stated trust boundary; the component does not install operating-system isolation.

The archive-only source invokes the accepted reader's origin, exact base/head/merge, protected-source and pagination checks, and compares intake and PR state before returning. It deliberately makes no Actions requests. A failing CI result therefore does not prevent archive capture, although the source still conservatively requires an otherwise valid configured open PR and approved sources. Capture snapshots the verified operator store's entire report inventory and checks its checkpoint around the durable append. A concurrent operator update leaves the already captured evidence intact but prevents successful reconciliation. Reconciliation also checks both stores again; a new intake event at that boundary is rejected. These checks do not make the two stores and GitHub one atomic transaction.

Material IDs include the source and complete canonical record digest. Edited comments add revisions; deleted comments remain in accumulated history. Repeated identical capture does not erase material or artificially change its classification context. Negative operator reports remain after a later positive report, and externally registered revisions remain separately represented. Tests establish these behaviors and require every historical revision, not just the latest comment, to receive a current classification. Captures cannot recover material deleted before any observation or discover external audits never registered.

The classification context binds the exact packet, schema-specific base/head binding, operator checkpoint and complete report inventory, accumulated material history, and immutable finding registry. New material, findings, packet contents, or operator state makes previous classifications insufficient. Every registered finding must remain in the candidate, retain its original body hash, and occur in the classifications of all its registered source materials. Missing findings, an omitted source link, a classification mapped to a different source, attempted registry replacement, and changed original bodies all fail the independent negative tests. Empty finding lists still require a recorded reason and observation. Whether that semantic judgment is correct remains trusted operator work; the code does not prove that a report contains no objection.

Successful reconciliation only checks intake consistency and a basic disposition shape. Independent acceptance receipts, complete disposition rules, dependency coverage, and current CI must still be checked by the later integration with the accepted schema-2 core. The current result explicitly reports `fresh_github_state_checked: false` and `verified_context_implemented: false`; `verify_context` always raises. A fresh publication snapshot and final freshness boundary are not implemented. All results retain `merge_authorized: false` and `deployment_eligible: false`. The live gate must remain inactive.

I also inspected the bounded optional probe and the three producer-supplied shape observations, and verified their index and source hashes. I did not independently repeat those authenticated requests. The samples record two push runs with the expected workflow path and a `run_attempt` field on each of 11 sampled jobs, plus a public PR run with no jobs and no PR association. The latter still fails the strict reader; the implementation introduces no fallback. These are unsigned local observations, not portable authentication or complete current-PR compatibility evidence. The probe performs at most five fixed-host GETs and exports selected response fields and hashes; the earlier compatibility caveats remain applicable outside those samples.
