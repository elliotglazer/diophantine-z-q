# Six-lemma Lean 4.35 verification handoff

This project is generated by
`python3 -B research/determinant-switch/verification/prepare.py --output NEW_DIR`
from the repository root. **Do not edit generated copies.** `SOURCES.json`
records the authoritative source paths, SHA-256 hashes and the sole lockfile
transformation; `MANIFEST.sha256` binds the generated inputs. Fresh generation
must give identical bytes. No compiled artifacts or absolute symlinks are part
of the handoff.

The scope is exactly the six names in `comparator.json`, under the definitions
in `Challenge.lean`. The arithmetic tensor-normalization claim stays open.
`CONTRACT.md` is a copied scope reference; its repository-relative reading links
belong to the original packet. Read the original packet's freeze report for
local results and reviewer decisions.

## Verification design

The repository's inherited default target is `ZInQ`, which excludes this
research module. This standalone project instead defaults to `BoundarySolution`,
whose only root is `Research.DerivativeSwitchBoundary`. The separate `Challenge`
library is never imported by the solution and is excluded from that default.
Both use the existing legacy-module syntax and the exact pinned dependencies.

The challenge has six intentional `sorry` theorem bodies, serving only as
specification placeholders. Its three definitions are concrete. The comparator
requires theorem declaration kinds to match, hence theorem holes rather than
new axioms. `definition_names` is empty: changing `AxesKernel`, `area` or
`action` cannot be accepted as a definition replacement. `sorryAx` is never
permitted in the solution. The conventional allowlist is `propext`, `Quot.sound`,
`Classical.choice`; the previously observed proofs use only the first two.

## Later Open Math OS run (not dispatched)

Use an approved Linux environment with pinned Lean 4.35.0 and working
`bubblewrap`. This is a future command specification, not evidence that Open
Math OS integration or Linux execution has been tested. Preserve the reviewed
manifest and challenge/config outside solution control, independently check
their hashes, and keep the project sources read-only during checking. Do not
accept modified theorem lists, definition holes or axiom allowances.

From this generated project, first verify the input hashes:

```sh
sha256sum -c MANIFEST.sha256
lean --version
lake --version
```

Materialize the nine dependencies at their locked revisions in this project,
using approved dependency setup. Do not run `lake update` or transplant macOS
compiled artifacts. If using the official Mathlib cache, request only the two
imports below and record the cache provenance; it is a trusted cache, not a
fresh dependency build. Cache setup executes pinned dependency code and should
run in the approved Linux environment with its intended setup permissions:

```sh
MATHLIB_CACHE_DIR="$PWD/.lake/mathlib-cache" lake exe cache get \
  Mathlib.Algebra.Module.Equiv.Basic Mathlib.Tactic.Ring
sha256sum -c MANIFEST.sha256
lake comparator --config comparator.json --paranoid
sha256sum -c MANIFEST.sha256
```

The comparator must exit zero, cover all six names, and show acceptance by
`Lean default`, `Lean paranoid`, `lean4lean`, `nanoda`, `con-leche`, and `con-ron`.
Capture its real exit code as well as stdout/stderr; piping to a logger without
preserving the command status is insufficient. A missing/failed checker leaves
the run incomplete or failed; do not silently drop it or disable sandboxing.
`--from-export` variants are not a substitute for this source-bound run.

The comparator builds and exports challenge and solution separately, compares
statements and referenced definitions, audits solution axioms, and replays the
solution through the selected kernels. There is no need to repeat a redundant
`lake check --paranoid`. If used separately, that command's default scope is
now the solution library, not the challenge or inherited `ZInQ` target.

Retain: frozen input manifest and source commit; toolchain and dependency
revisions/cleanliness; OS/architecture and sandbox outcome; exact commands,
stdout/stderr and exit codes; checker binary versions/hashes and individual
outcomes; cache provenance; and exported-file hashes if the runner preserves
exports. Standard Lake uses temporary exports, so do not invent retained
export hashes if they were not captured. No checker count establishes semantic
truth or independence of mathematical reasoning. Runtime, resource limits and
export retention on Open Math OS remain to be agreed when dispatch is authorized.

warnings. Local preparation is not Linux sandbox execution, protected comparator
