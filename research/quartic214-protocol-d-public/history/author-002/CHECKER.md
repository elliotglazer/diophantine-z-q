Run from the repository root:

```sh
python3 -B research/quartic214-protocol-d-public/check_records.py --self-test
python3 -B research/quartic214-protocol-d-public/check_records.py --require-scoped-review
```

The second additionally requires actual non-author decisions for `applications`, `coverage`, `public-adoption` and `assembly`, bound to the current record and source files. Initial-interface rows identify complete inline application derivations. Such a row may have the same supplying and consuming passage: it is a summary interface for reconciliation, not an additional circular premise. The separately named direct-transition rows expose the changed and retained joins. Each records the literal available assertion, assertion needed next, actual object identity, domain, normalization and distinct supplier/derived-output tokens. A connecting-derivation record pins its argument, every listed extra premise, the exact available-input contract and its derived-output contract. Consumers bind that derived contract; a weaker source is never silently relabeled as the final conclusion. Full application requirements and maps are in the linked fourteen contracts, each with nine named obligations. The coverage index partitions every line of the current assembly, every linked proof and every selected textual source. It links consumer, supplier, derivation and extra-premise uses. Every partition is classified as current inference, application-scoped source/argument, historical/scope prose or superseded historical derivation. A substantive partition needs an actual use or named application scope; line-count coverage alone is insufficient. Exact application-scope links use the contract's actual source inventory and do not manufacture per-line dependency edges. Independent source completeness remains with the coverage reviewer. Exact recursively retained public source inventories are linked through `source-carry-sources.json`, rather than copied or newly accepted here.

The checker validates file and passage hashes, line coverage without gaps/overlaps, all initial reconciliations, references in both directions, every declared direct supplier edge, literal supplier matching, separately bound connecting derivations and additional premises, derived-output/consumer matching, the fourteen application identities, required nine-obligation fields and source pins. It rejects unresolved required reconciliation, omitted or orphan edges, missing referenced uses, stale supplier fingerprints, unsupported exclusions and author-generated finding decisions. An author-proposed response remains separate from a reviewer disposition.

Reviewer-authored `review/*.json` decisions may declare `reviewer`, `role`, `decision`, `scopes` and `bound_files` (repository-relative path to SHA-256). The supported role is `non-author internal model reviewer`; decision is `accepted`, `pending` or `rejected`. Each acceptance must bind the integration record, checker semantics and every declared source/contract file. Extra evidence may use a different schema; the checker consumes only explicit decision objects. Reviewers should record requested-model metadata and its limitations. These declarations support exact scoped mathematical review; they do not establish trusted controller eligibility. An author identity cannot accept an application that lists that identity as an author.

The self-test mutates in-memory copies and rejects: omitted named-theorem, section-only and unnamed-estimate edges; deletion of a use still referenced by coverage; unresolved required reconciliation; loss of a required obligation; changed proof without fresh binding; self-approval; coherent weakening of a supplier and its consuming author records with an old review binding; changed proof with an old review; deletion of a listed connecting premise; and deletion of the connecting derivation. A synthetic review exists only inside the negative-control test and is never written as evidence. The coherent-weakening check establishes invalidation of an existing frozen decision. With no decision, coherent author revisions can remain structurally consistent and must still undergo source-level review; the checker cannot decide arbitrary implication strength.

These are finite record properties. They do not establish mathematical truth, exhaustive source reconstruction, honest reading, reviewer epistemic independence, an effective threshold, or any particular defining member. The required public protected controller/App decision remains separate.
